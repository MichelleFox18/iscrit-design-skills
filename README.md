# Дизайн — пространство роста

Внутренняя платформа развития дизайн-команды. Next.js 16, React 19,
TypeScript, Tailwind CSS 4, PostgreSQL 17. Визуальный стиль основан на
предоставленных референсах: белый, Sky Blue `#D0E6FF`, Purple `#453C69`,
Orange `#ED8D48`, крупная типографика, прямоугольные блоки и кнопки-пилюли.

## Текущий статус

Работают публичные страницы, авторизация, три роли, кабинеты,
самооценка и независимая оценка руководителя, семь этапов review,
согласованный результат, цели, материалы, избранное, история,
управление пользователями/сроками/контентом и аудит.

**Исходная методология ещё не импортирована.** Google Sheets недоступен
в среде (прокси вернул CONNECT 403); нужен XLSX со всеми вкладками и
формулами. Каталог и циклы в рабочей базе намеренно пустые. Нельзя считать
MVP полностью готовым или формулы сверенными с таблицей до этого импорта.
Не создавайте демонстрационные компетенции вместо оригинальных.

Расчёт сейчас реализует требования задания: четыре равновесные области,
13 общих компетенций 4/3/3/3, минимум 11 числовых оценок и 3/2/2/2 по областям,
исключение Н/П/пустых, пороги 1.5/2.5/3.5 без округления до определения грейда.
Отдельные треки не входят в общий балл. Эти правила подлежат сверке с XLSX.

## Локальный запуск

Нужны Node.js 24 (проверено на 24.19), npm 11, Docker с Compose.
Используйте существующий checkout; отдельный Git worktree не требуется.

```bash
npm ci
npm run env:local
docker compose --env-file .env.local up -d --wait
npm run db:setup
npm run dev
```

Команды запускаются из корня репозитория. Next.js использует порт 3000,
PostgreSQL — 54329, доступный только через loopback. Docker volume сохраняет
БД между перезапусками. `.env.local`, зависимости, сборка и backup не коммитятся.

`env:local` создаёт случайные локальные пароли БД и сохраняет существующий
`.env.local`, не меняя его. Для ручной настройки можно скопировать `.env.example`
в новый `.env.local` и отредактировать значения.

`.env.example` содержит только примеры для локальной разработки, без
реальных ключей. Пароли `POSTGRES_PASSWORD` и в `MIGRATION_DATABASE_URL`
должны совпадать; `APP_DATABASE_PASSWORD` — совпадать с `DATABASE_URL`.
В подготовленной среде уже записаны случайные локальные пароли БД.
Не заменяйте существующий `.env.local` командой копирования.

`db:setup` идемпотентно создаёт схему и непривилегированную роль `design_app`.
Это схема начального MVP, а не миграционный менеджер для следующих релизов.
Скрипт не перезаписывает пароли уже созданных пользователей и не подменяет
матрицу. Демоданные включаются только `SEED_DEMO=true` вне production.

### Тестовые аккаунты

| Почта | Роль | Доступ |
| --- | --- | --- |
| designer@design.local | Дизайнер | Своя карточка |
| lead@design.local | Руководитель | Мария · демо, назначенная ему |
| admin@design.local | Администратор | Пользователи, циклы, методика, материалы, аудит |
| other@design.local | Дизайнер | Никита · демо; не назначен этому руководителю |

При стандартном локальном seed пароль всех аккаунтов: `Design-Demo-2026!`.
Для собственной установки задайте `DEMO_PASSWORD` до первого seed.
Имена и аккаунты синтетические. Нет демонстрационных грейдов и
придуманных описаний компетенций. В базу добавлены три настоящих внешних
ресурса W3C, Material Design и Figma; это полезные материалы, не данные матрицы.

## Как работать с платформой

1. Получить исходный XLSX, разобрать все вкладки и сверить правила.
2. Войти администратором → «Управление» → «Матрица и треки».
3. Перенести точные названия, пояснения и уровни; указать источник,
   подтвердить сверку и опубликовать версию. На текущем этапе самостоятельно
   отмечать методологию сверенной нельзя: исходная книга ещё не получена.
4. В разделе «Циклы оценки» создать период, выбрать методику, дату и участников.
5. Дизайнер заполняет и сохраняет каждый ответ, затем отправляет самооценку.
6. Руководитель заполняет отдельные ответы и публикует их; обе стороны видят разницу.
7. После встречи руководитель фиксирует согласованные ответы; обе стороны
   подтверждают результат. Исправление подтверждённого итога требует причины
   и сбрасывает подтверждения. После review балл считается только по итогам.
8. В плане выбираются максимум одна общая и одна цель трека. Прогресс
   доступен после двух подтверждений. Можно приложить ссылки, отметки и материалы.
9. Карточка завершается и остаётся в истории. План продолжает действовать;
   состав целей на момент завершения сохраняется отдельным снимком.

Администратор редактирует материалы формами, назначает руководителей,
отключает аккаунты, меняет плановую дату review и архивирует завершённые циклы.
Изменение матрицы создаёт новую версию: прошлые описания и итоги сохраняются.

## Безопасность и данные

- Авторизация: scrypt с индивидуальной солью; случайные непрозрачные сессии,
  в БД хранится только SHA-256 токена. Cookie HttpOnly, SameSite=Lax,
  Secure в production; срок 7 дней. Есть ограничение попыток входа.
- Mutation endpoints проверяют Origin, сессию, роль, назначение, состояние и ревизию.
  Zod проверяет входные данные и HTTP(S)-ссылки.
- PostgreSQL runtime не является владельцем таблиц, не имеет SUPERUSER/BYPASSRLS.
  RLS ограничивает личные карточки, цели, избранное и черновики руководителя.
- Самооценки не редактируются руководителем. Журнал создаётся триггерами
  в той же транзакции; приложение не может его удалять или изменять.
- Данные в клиент передаются через серверный слой доступа без хешей паролей
  и токенов. Персональные страницы динамические, без общего кеша.
- Внутренние материалы не возвращаются гостям. Прямой чужой URL не открывает карточку.
- В этой версии подтверждения — ссылки и текст; файлы не загружаются.

Для production используйте отдельную БД без демоаккаунтов, собственные
пароли, `SEED_DEMO=false`, `APP_ORIGIN` с каноническим HTTPS-адресом,
HTTPS reverse proxy и ограниченный доступ к БД. Миграционные реквизиты
нужны только процедуре установки; Next.js runtime достаточно `DATABASE_URL`.
Почтовые приглашения, SSO и самостоятельное восстановление пароля пока
не реализованы: аккаунты и смена пароля управляются администратором.

## Проверки

```bash
npm test
npm run typecheck
npm run build
npm run test:integration
```

Интеграционный тест требует локального PostgreSQL, уже созданной роли
`design_app` и свободного порта 3100. Он создаёт отдельную временную БД,
запускает production-сборку, проверяет RLS/API и полный review, затем
останавливает свой процесс и удаляет только эту тестовую БД.
Технические критерии существуют только в тесте и не становятся рабочей методикой.

Проверка браузера (на запущенном `npm run dev` со стандартным локальным seed):

```bash
npx playwright install chromium
npm run test:browser
# Или уже установленный системный Chromium:
CHROMIUM_PATH=/usr/bin/chromium npm run test:browser
```

Браузерный сценарий проверяет публичные страницы на 1440/768/390px,
вход трёх ролей, ограничения URL, избранное, назначенную команду,
административные формы и мобильный выход. Скриншоты — в `test-results/`.
Полный аудит WCAG AA ещё не выполнен.

## Резервное копирование

```bash
npm run backup
bash scripts/verify-backup.sh backups/<имя-файла>.dump
```

Backup создаётся `pg_dump --format=custom` с доступом только владельцу файла.
Проверка восстанавливает копию в отдельную временную БД, проверяет наличие
администратора, RLS и политики доступа и удаляет свою временную БД.
Живая база не перезаписывается. Периодическое выполнение, шифрование,
внешнее хранение, retention и проверка полной авторизации после аварийного
восстановления должны быть настроены перед эксплуатацией.
Пароли ролей БД не входят в dump: восстановите `design_app` отдельным
bootstrap шагом и используйте собственные реквизиты, не извлекайте их из backup.
